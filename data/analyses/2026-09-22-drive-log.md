## For the operator
- **Capture-start vs drive-window conflict (defect, not fixed from the road).** `POST /control/capture` returns a bare 500 `failed_step: profile_activation` whenever a `drive` window is open: the route calls `capture_controller.start_capture`, which raises `CaptureConflictError` ("a capture is already active"), and the handler mislabels it (failed_step never advances past `profile_activation`) and drops the reason. Each failed attempt also rotated the writer to a fresh default session (`2026-09-22T170423`, `…T170453`). The protocol says to open the drive window first and start `tuning` later, so every drive hits this. Choose: (a) the profile capture ends and resumes the drive window itself (cost: the handler does more); (b) refuse with a 409 that says "stop the drive window first" (cheap and honest, but the drive window still has a gap); (c) let a drive window and a profile capture coexist (the tag-routing change is the largest). Workaround used today: stop the window, start the capture, reopen the window after the capture stops.
