# W02.1 — does `21 10` answer outside session 0xC0? (KOEO probe, 2026-09-22)

**Answer: no.** In the default session the ECM refuses the calibration-id
read with NRC 0x80 (`serviceNotSupportedInActiveDiagnosticSession`). The id
must be read inside the Mode-22 session, i.e. it rides the DID window — the
design W02.2 already ships for `session: extended`. `data/dids.yaml`
`access.calibration_id.session` is now `extended`.

## Wire evidence (`candump -t z can0,7E0:7FF,7E8:7FF` on the Pi during the resend)

```
(001.085202)  can0  7E0   [8]  02 21 10 00 00 00 00 00     <- our request, single frame, len 2
(001.085579)  can0  7E8   [8]  03 7F 21 80 00 00 00 00     <- ECM: negative response, NRC 0x80
```

377 µs turnaround. The surrounding `10 10 41 0C …` / `30 00 …` / `21 0D …`
frames are the collector's ordinary batched Mode 01 polling continuing
underneath, i.e. the ECM was in its default session at that instant.

Two earlier sends (02:01:26.6, phase mode01, next window 28 s) got the same
outcome from the endpoint's point of view; candump was only attached for the
third.

## Controls

- **Request path works** (same second, default session):
  `01 0C` @7E0 → `41 0C 00 00` (RPM 0.0); `01 05` @7DF → `6C` (68 °C).
- **A refusal is visible**: `21 FF` (undefined local id) also drew no
  positive response — see the defect below for why the endpoint could not
  tell that apart from silence until now.
- **In-session read works**: the daemon's W02.2 window read had already
  produced `/status.ecu_calibration_id = 1ZS44A00000`,
  `calibration_matches_registry = true` on this daemon. Historical: `61 10
  <ASCII>` inside 0xC0, 2026-09-20 KOEO (`probe_local_identifier` sweep).

## Defect found on the way

`/control/obd_request` returned `responded: false, raw_hex: null` for the
NRC. The ECM *answered*; the endpoint called it silence. `CanObdClient.query()`
collapses a negative response to `None`, and `execute_ad_hoc_request` has no
NRC field at all — "an empty result must say which kind of empty it is"
(AGENTS.md). Fixed in the same commit: the ad-hoc result now carries
`negative_response_code` and its name, and `responded` is true for an NRC.
Also `NRC_NAMES` lacked 0x80, so the daemon would have called it
`unknown (0x80)`.

## What this settles for W02

`session: default` (read at connect, on every reconnect, for free) is ruled
out for this ECM. `extended` is the measured answer and the code path W02.2
already runs. A different ECU program may differ; re-probe before assuming.
