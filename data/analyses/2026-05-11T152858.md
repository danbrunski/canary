## Confirmed findings

See `data/bindings.yaml` for the canonical record. Highlights from this session:

### High-confidence

- **`0x551:0` — Coolant temperature** with offset -40 °C. Monotonic 53 → 90 raw
  across the 6-minute run, decoding to 13 → 50 °C. Classic warm-up arc.
- **`0x23D:1+2` — RPM or load (directionally confirmed)**. Both bytes spike
  together and order correctly across rev levels:
  - idle: 0/0 → 2k: 27.8/24.0 → 2500: 29.7/24.3 → 3k: 31.3/26.2 → 4k: 42.5/37.4
- **`0x233:1` — Intake vacuum or IAC**. 227 at warm idle, drops during blips,
  zero engine-off. Inverse-throttle pattern.
- **`0x231:0` ≡ `0x231:3` ≡ `0x29E:0` — Engine-running state code**. 254 = off,
  205 = running. Three-way cross-broadcast for redundancy.

### Medium-confidence

- **`0x233:4` ≡ `0x23D:3` — Calc load (or similar)**. Cross-broadcast pair,
  cranking spike, drops with sustained load.

### Hypothesized

- **`0x23D:6` — Throttle transient indicator**. Bursts during throttle
  transitions, return to zero at steady state. Behavior is **inconsistent
  with an earlier seated-session reading** where the same byte appeared to
  latch 0 → 255 — the earlier interpretation was likely misled by NT510
  screen-selection tags rather than physical actions.

## Lessons learned vs. earlier session

The earlier session (2026-05-11T034516) tagged NT510 screen selections (e.g.
`ecm_livedata_maf`, `ecm_livedata_rpm`). Those tags didn't correspond to
physical state changes on the vehicle, so the windows weren't sharp enough
to differentiate bytes cleanly. Several "candidate" bindings from that session
(notably the `0x23D:6` engine-state-flag interpretation) appear to have been
artifacts of the tagging methodology rather than real signal-byte mappings.

The rev protocol's two innovations that fixed this:

1. **Physical-action boundaries** (idle, blip-start, blip-end, recovery) match
   actual ECM state changes 1:1.
2. **Bookend engine-off windows** at start and end isolate which bytes are
   "engine running" only vs. always-broadcast.
